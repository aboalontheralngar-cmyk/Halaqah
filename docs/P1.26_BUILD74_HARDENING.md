# P1.26 Build 74 — hardening, repair and audit close-out

**Version:** `4.3.0-alpha.20+74`  
**SQLite:** `24` — لا تغيير في مخطط البيانات المحلي  
**Date:** 2026-08-12

## الهدف

Build 74 يغلق ملاحظات التدقيق الأربع عشرة السابقة من دون إعادة كتابة المشروع أو كسر بيانات P1.26، ويضيف إصلاحًا مخصصًا لحالة بوابة الجهات الإشرافية التي كانت تعرض رسالة عامة تطلب تنفيذ P7.3 رغم أن جداول الإشراف موجودة في القاعدة.

## 1 — تاريخ اليوم في الويب

أضيف `localDateKey/localDateKeyOffset/localDateFromKey` في `website/src/utils/dateUtils.ts`، واستبدلت حسابات تاريخ الأعمال المبنية على `toISOString()` في الحضور والتسميع والنقاط والخطط والصندوق والتقارير والإجازات والاختبارات والإشعارات والإشراف. الطوابع الزمنية الحقيقية `created_at/updated_at` تظل UTC كما يجب؛ التغيير يخص حقول اليوم `DATE` فقط.

## 2 — قفل اعتماديات Flutter

- أزيل تجاهل `*.lock` من `.gitignore`.
- ثُبتت إصدارات الاعتماديات المباشرة في `pubspec.yaml` بدل حدود caret.
- أضيف `tools/verify_source_prerequisites.*` ليولّد `pubspec.lock` على جهاز Flutter إذا كان مفقودًا ويمنع Release إذا لم يُنشأ.
- لا يوجد Flutter SDK داخل بيئة تحرير هذه الحزمة، لذلك لم يُصطنع `pubspec.lock` يدويًا؛ يجب أن يولده Pub الحقيقي ثم يُحتفظ به.

## 3 — فصل بيئات Supabase

أضيف `lib/services/cloud_config.dart`. Debug يسمح بتوافق مشروع التطوير القديم؛ Staging/Production Release يتطلبان إعدادًا صريحًا. Production لا يقبل fallback. عُدّلت أدوات Build وGitHub workflow لتمرير `HALAQAH_ENV` وقيم Supabase المعلنة.

## 4 — QR القديم

أزيل مفتاح HMAC القديم الثابت من المصدر. قراءة QR legacy متوقفة افتراضيًا ولا تُفعّل إلا عبر `HALAQAH_LEGACY_QR_SECRET` أثناء انتقال مخطط ومدروس، مع فحص عمر timestamp وانحراف المستقبل. QR الحالي العشوائي غير الكاشف للمعرف لم يتغير.

## 5 — تخفيف الملفات الضخمة

تمت أول تجزئة منخفضة المخاطر في الإصدار نفسه:

- دورة إنشاء/ترقية SQLite انتقلت إلى `lib/services/local_database_schema.dart`، فانخفض `database_service.dart` بنحو ألف سطر مع بقاء schema version 24.
- إعداد البيئة انتقل إلى `cloud_config.dart`.
- التسجيل التشغيلي انتقل إلى `app_logger.dart` و`operationalLog.ts`.
- عقد الإشراف في الويب انتقل إلى `services/supervisionService.ts` بدل تكراره داخل الصفحة/store.

لم تُفصل الشاشات العملاقة قسرًا في hotfix واحد؛ هذا مقصود لتجنب regression بصري واسع من دون Flutter SDK، لكن Build 74 يضع حدودًا واضحة للتجزئة اللاحقة بدل زيادة الخدمات المركزية.

## 6 — اشتراكات Zustand

كل الاستدعاءات الواسعة `useStore()` في صفحات الويب حُولت إلى selectors باستخدام `useShallow`. هذا يقلل إعادة التصيير عند تغير أجزاء غير مرتبطة من المتجر.

## 7 — Flutter lint baseline

`analysis_options.yaml` أصبح يحتوي قواعد correctness/privacy فعلية و`avoid_print` كخطأ، من دون إضافة dependency lint جديدة إلى hotfix غير قابل لتشغيل Flutter داخل بيئة التحرير.

## 8 — السجلات والأخطاء

- أضيف `AppLogger` في Flutter؛ لا يطبع الرسالة الخام أو payload أو معرفات السجلات.
- أزيلت `print()` من `lib/`.
- أضيف `logOperationalError()` للويب واستبدلت به `console.error/warn` التي كانت تمرر أخطاء Supabase الخام. في Production لا يكتب المتصفح تشخيصًا خامًا.
- سجل الحوادث الموجود يحفظ نوع الخطأ وبصمة stack منقحة فقط.

## 9 — العمليات متعددة الخطوات

أضيفت RPCs ذرية للأسرة:

- `delete_family_atomic`
- `set_family_students_atomic`
- `save_family_guardian_atomic`
- `delete_family_guardian_atomic`

تشمل unlink الطلاب، تبعيات البوابة/التقارير، تبديل ولي الأمر الرئيسي وتحديث هاتف الطلاب وسجل التدقيق داخل المعاملة نفسها.

## 10 — فحوص أقوى

- أضيف validator خاص بـBuild 74 يحمي التاريخ المحلي، selectors، عدم تسريب logs، QR، CloudConfig، SQL الذري وsearch_path.
- أضيف اختبار runtime فعلي لحد منتصف الليل في `Asia/Aden` وتصنيف أخطاء الإشراف؛ أصبح مجموع بوابات الإصدار 56.
- أضيف Supabase readiness SQL قرائي يفحص جداول/RPC/RLS/عضوية المالك والعقد الذري.
- بقيت اختبارات Flutter وNext الحقيقية داخل CI؛ لا يُعتبر validator النصي بديلًا عنها.

## 11 — حزمة المصدر والخطوط

أضيف preflight صريح لملفات Tajawal. الحزمة الكاملة لهذا التسليم تظل source-upgrade ولا تتضمن binaries المفقودة في المصدر الذي استلمناه. حزمة الملفات المعدلة هي الخيار الموصى به فوق المشروع الموجود.

## 12 — تشديد SECURITY DEFINER

تم فحص كل دوال `SECURITY DEFINER` في ملفات Supabase الموجودة؛ كل تعريف حالي يثبت `search_path` ويتضمن `pg_temp`. دوال Build 74 الجديدة تسحب EXECUTE من `PUBLIC/anon` وتمنحه لـ`authenticated` فقط حيث يلزم.

## 13 — مسار SQL موحد

أضيف:

- `website/supabase/P1.26_BUILD74_APPLY.sql` — ملف تطبيق واحد.
- `website/supabase/P1.26_BUILD74_VERIFY.sql` — ملف فحص واحد قرائي.

لا يستبدلان تاريخ migrations، لكنهما يمنعان المستخدم من تجميع ملفات P7.3/P1.20 القديمة يدويًا لهذا الإصلاح.

## 14 — نظافة الإصدار والمنصات

- رُفعت النسخة إلى Build 74.
- وُحد عدد validators في README/website README مع العداد الفعلي.
- وُثقت المنصات المدعومة رسميًا: Android + Web. ملفات iOS/macOS/Linux/Windows الموجودة Flutter scaffolding وليست Release targets؛ لذلك لم نخترع bundle IDs إنتاجية لها.

# إصلاح بوابة الجهات الإشرافية

المخطط الحالي يحتوي الجداول الأساسية، لذلك Build 74 لا يعامل الخطأ كـ«P7.3 لم تنفذ». Migration الإصلاح:

- يزيل عضويات الإشراف المكررة قبل إعادة unique index.
- يعيد عضوية `owner` من `supervisors.owner_id` ويحافظ عليها عبر trigger.
- يعيد RPCs والسياسات والمنح المطلوبة.
- يجعل `get_my_supervisors()` يكتشف المالك مباشرة حتى عند قاعدة عانت من تطبيق جزئي سابق.
- يضيف `get_supervision_health()` لتشخيص جاهزية الحساب والعقد.
- يضمن عقد `supervision_visits` المستخدم في P1.20.
- يضمن وجود قيمة `supervisor` في `public.user_role` قبل الإصلاح.

الواجهة أصبحت تعرض سببًا محددًا بدل الرسالة العامة، وتستخدم الفحص الصحي عندما يفشل dashboard أو الإنشاء أو الزيارات أو دعوات الفريق.

## التحقق الذي يجب إكماله على جهاز المالك

بيئة التحرير الحالية لا تحتوي Flutter SDK ولا اتصالًا بقاعدة Supabase الخاصة بالمالك، كما تعذر `npm ci` هنا بسبب عدم توفر DNS لسجل npm. لذلك نجحت بوابات المصدر/runtime المتاحة، بينما تبقى الخطوات التالية مطلوبة بعد تطبيق الحزمة:

1. تشغيل `P1.26_BUILD74_APPLY.sql` على Supabase الحقيقي.
2. تشغيل `P1.26_BUILD74_VERIFY.sql` والتأكد من أن كل `passed=true`.
3. `flutter analyze` ثم `flutter test` على جهاز Flutter.
4. `npm ci && npm run quality:ci` أو أداة Windows.
5. اختبار إنشاء/فتح جهة إشرافية وربط مركز ودعوة محلل بحسابات تجريبية.
