# P1.22 — سجل تنفيذ دفعة التشغيل اليومية

> تاريخ التنفيذ البرمجي: 2026-08-08
>
> نسخة المشروع بعد الدفعة: `4.3.0-alpha.15+66 (P1.22)` — SQLite `22`.
>
> **حالة التنفيذ الخارجي:** أكد مالك النظام في 2026-08-08 تنفيذ migration P1.22 ونجاح `verify_p1_22.sql`. لقطة التحقق المرفقة أكدت أن `closing_respects_activity_exemption` و`closing_respects_full_pause` كلاهما `true`.

## القرارات التشغيلية المعتمدة

1. **النشاط حضور حقيقي وليس غيابًا ولا استئذانًا.** عند تسجيل محاضرة/نشاط/دوري/عشاء/رياضة/مسابقة ثقافية يظهر الطالب حاضرًا، ويُعفى من إلزام التسميع لذلك اليوم ما لم يُسجل له تسميع فعلي.
2. **التوقف المؤقت منفصل عن إيقاف التسميع.** إيقاف التسميع يسمح باستمرار التحضير، بينما التوقف الكامل للدراسة/العمل/الظرف يعفي من الحضور والتسميع خلال المدة ولا يُعامل كغياب.
3. **التلقين مسار مستقل.** لا يرفع المحفوظ ولا يتحول تلقائيًا إلى مراجعة، لكنه يثبت أن الطالب أدى نشاطًا قرآنيًا لذلك اليوم فلا يدخل في «لم يسمّع».
4. **P1.22 محلي أولًا مع توافق انتقالي.** SQLite يحتفظ بالحقول والجداول الجديدة فور الترقية. مسار التوافق المحافظ مع P1.21 باقٍ لحماية البيانات عند الاتصال ببيئة سحابية أقدم، بينما بيئة المالك الحالية أُبلغ عن ترحيلها بنجاح إلى P1.22.
5. **تسجيل Google لا يلتف على صلاحيات المركز.** OAuth يثبت هوية المستخدم فقط؛ صلاحية الوصول إلى الحلقة/المركز تبقى مرتبطة بعضوية Supabase الحالية ولا يُنفذ ربط تلقائي اعتمادًا على البريد وحده.

## تغييرات SQLite 22

- إضافة الحقول التالية إلى `daily_records`:
  - `activity_type`
  - `activity_note`
  - `recitation_exempt`
  - `talaqqin_done`
  - `talaqqin_amount`
  - `talaqqin_note`
- إضافة `scope` إلى `student_holds` بالقيمتين `recitation_only` و`full_pause`.
- إنشاء `talaqqin_records`.
- إنشاء `student_admin_actions`.
- إدخال الجداول الجديدة في النسخ الاحتياطي والاستعادة.
- إضافة فهارس وتدقيق للتغييرات الجديدة.

تتم ترقية قاعدة الجهاز محليًا عبر `DatabaseService` عند فتح النسخة الجديدة، ولا يحتاج المستخدم إلى تشغيل SQL يدوي لـSQLite.

## Supabase — منفذ ومتحقق لدى المالك

ملف الترحيل المستخدم، ويُعاد استخدامه عند تجهيز أي بيئة Supabase جديدة:

`website/supabase/migrations/20260808000100_p1_22_activity_talaqqin_admin.sql`

وفحص ما بعد التنفيذ:

`website/supabase/verify_p1_22.sql`

التفاصيل وخطوات Google موثقة في:

`docs/P1.22_SQL_AND_GOOGLE_SETUP.md`

### ما يفعله migration

- يضيف حقول النشاط/الإعفاء/التلقين إلى `attendance`.
- يضيف `scope` إلى `student_holds`.
- ينشئ `talaqqin_records` و`student_admin_actions` مع RLS.
- يحدّث `close_daily_operations` ليحترم النشاط والتلقين والتوقف الكامل وموازنة السلوك.

### سلوك التوافق مع بيئة سحابية أقدم

- رفع الحضور يحاول مخطط P1.22 أولًا ثم يتراجع إلى الحقول القديمة عند غياب الأعمدة الجديدة.
- تنزيل الحضور القديم يدمج السجل ولا يمحو نشاط/تلقين/إعفاء P1.22 الموجود محليًا.
- جداول التلقين والإداريات تبقى محلية حتى تصبح الجداول السحابية موجودة.
- هذا مسار انتقال وليس بديلًا عن تنفيذ migration قبل اعتماد مزامنة جهازين للميزات الجديدة.

## نتائج التحقق في بيئة التطوير

### ناجح

- **50/50 بوابة إصدار**: جميع فحوص `website/scripts/run-all-validations.mjs` نجحت.
- فحص صياغة TypeScript للملفات المعدلة نجح باستخدام TypeScript `5.8.3` المتاح في البيئة.
- `AndroidManifest.xml` صالح XML.
- `ios/Runner/Info.plist` اجتاز `plutil -lint`.
- `website/package.json` صالح JSON.
- فحص ساكن لـ **184 ملف Dart**: لا استيرادات محلية مفقودة، لا علامات تعارض، وبنية الأقواس/السلاسل/التعليقات متوازنة بالفاحص الساكن.
- فحص ساكن لـSQL: معاملة `BEGIN/COMMIT` واحدة، أزواج `$$` متوازنة، ولا `DROP TABLE` أو `TRUNCATE` أو `DROP SCHEMA`.

### لم يُشغّل في هذه البيئة

- `flutter analyze`
- `flutter test`
- بناء APK/IPA
- اختبار OAuth Google على جهاز/نطاق فعلي

السبب في الثلاثة الأولى: Flutter/Dart SDK غير موجود في بيئة العمل الحالية. لذلك لا تُعامل الفحوص الساكنة كبديل عن تشغيل Flutter على جهاز التطوير قبل الإصدار الإنتاجي.

## P1.22 build 66 hotfix (2026-08-08)

- Fixed Flutter compilation in the student period/WhatsApp report by importing `daily_record.dart` for `DailyActivityType`.
- Study-day suspension now preserves all manually entered `daily_records`; suspended dates are excluded by policy instead of deleting history.
- The P1.22 Supabase migration now bootstraps `public.student_holds` when an older deployment is missing the P3 migration, then applies `scope`, trigger, RLS, and the P1.22 closing logic.
- Student-hold cloud sync now tolerates a missing remote table until the owner runs the migration.
- The previous SQL failure `42P01: relation public.student_holds does not exist` is therefore addressed in this build.
