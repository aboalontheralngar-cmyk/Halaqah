# قرار التوسع: Supabase أم Firebase؟

## القرار

الاستمرار مع Supabase/PostgreSQL هو المسار الأقل مخاطرة للمشروع الحالي. لا توجد حاجة تقنية إلى نقل شامل إلى Firebase لمجرد الانتقال من محافظة إلى عدة دول.

## لماذا

- البيانات مترابطة: جهات، مراكز، حلقات، طلاب، أسر، حضور، تسميع، خطط، تقارير، وصلاحيات. PostgreSQL مناسب لهذه العلاقات والتقارير.
- المشروع استثمر بالفعل في RLS وRPC وترحيلات واختبارات عقود؛ إعادة البناء على Firestore ستغير نموذج البيانات والاستعلام والصلاحيات والمزامنة.
- Supabase يوفر ترقية موارد الحوسبة وRead Replicas وتوجيه قراءة جغرافيًا عند الحاجة. راجع [وثائق Read Replicas](https://supabase.com/docs/guides/platform/read-replicas) و[الحوسبة والقرص](https://supabase.com/docs/guides/platform/compute-and-disk).
- Firestore يدعم التخزين المؤقت والعمل دون اتصال على Android وApple، ثم يزامن التغييرات ويستخدم «آخر كتابة تفوز» عند تعدد التغييرات على الوثيقة، وفق [وثائق Firebase الرسمية للعمل دون اتصال](https://firebase.google.com/docs/firestore/manage-data/enable-offline). هذه ميزة جيدة، لكنها لا تلغي تكلفة إعادة هندسة العلاقات والتقارير.

## خطة توسع Supabase

1. قياس الاستعلامات البطيئة وإضافة فهارس مدروسة.
2. فصل بيانات كل مركز/جهة بعقود RLS واختبارات تسرب.
3. ترقية Compute وDisk IOPS قبل تغيير التقنية.
4. إضافة Read Replica إقليمية عندما تصبح القراءة العالمية هي عنق الزجاجة.
5. أرشفة سجلات التدقيق والتاريخ القديم بسياسة احتفاظ معلنة.
6. اختبار استعادة النسخ، لا الاكتفاء بإنشائها.
7. مراقبة حجم الجداول، الاتصالات، زمن RPC، ونسبة أخطاء Edge Functions.

## متى نعيد تقييم Firebase؟

إذا أصبح المنتج الجديد مستقلًا بنموذج وثائقي بسيط ويحتاج SDK مزامنة لحظية أصلي أكثر من حاجته إلى التقارير العلائقية. حتى حينها يفضّل بناء تجربة محدودة لا ترحيل المنصة كلها دفعة واحدة.
