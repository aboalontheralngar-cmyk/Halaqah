**Owner evidence date:** 2026-08-09  
**Release:** `4.3.0-alpha.19+73 (P1.26)`  
**Purpose:** record the exact Supabase state supplied by the owner and the safe next migration.

## Confirmed current state

The owner-provided schema shows a shared `public` schema containing pre-existing tables from another operational workload (for example `Subscribers`, `Readings`, `Fillings`, `Collections`, `Expenses`, `SubscriberPoints`, and `AppNotifications`). These tables are not Halaqah tables and must not be altered by Halaqah migrations.

- `profiles`
- `supervisors`
- `centers`
- `halaqat`
- `center_members`
- `families`
- `family_guardians`

The supplied audit screenshots still show the Halaqah core/learning surfaces as absent, including `students`, `attendance`, `memorization`, `points`, `exams`, `exam_scores`, `vacations`, `fund_transactions`, `notifications`, `plans`, `student_holds`, `talaqqin_records`, `student_admin_actions`, `quran_courses`, and `quran_course_enrollments`.

## Safe next step

Use `website/supabase/P1.26_POST_BOOTSTRAP_CORE.sql`.

This script is derived from the already reviewed P1.25 additive compatibility migration, but is now explicitly guarded for the owner-provided post-bootstrap schema. It:

1. requires the complete Halaqah base scope before creating core tables;
2. checks UUID/text scope types before any core creation;
3. creates or repairs only Halaqah core/learning tables;
4. installs current scope helpers, RLS, foreign keys, indexes, plans, courses, holds, Talaqqin and administrative action surfaces;
5. does not contain `DROP TABLE`, `TRUNCATE`, or row deletion;
6. does not mutate the unrelated operational tables listed above.

After a successful commit, run `website/supabase/P1.26_POST_BOOTSTRAP_VERIFY.sql`. The final recommendation should be `READY_FOR_APP_SYNC_TEST`.

## Operational boundary

The existing mixed Supabase project can technically host the Halaqah tables because there are no exact table-name collisions in the supplied schema. Long term, a dedicated Supabase project for Halaqah remains cleaner for backup, RLS review, billing and incident isolation. No migration in P1.26 moves or deletes the existing unrelated workload.
